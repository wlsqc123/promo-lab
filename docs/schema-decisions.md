# 정산 스키마 설계 근거

작성일: 2026-10-13  
구현: `sql/schema.sql`, `sql/init.sql` · 검증: `sql/check_schema.sql`

## 테이블과 키

입력 점수, 정산 결과, 누적 잔액, 청크 완료 기록을 나눠 저장합니다. 장애가 생기면 원본과 결과를 비교하고 어디까지 처리됐는지 확인합니다.

| 테이블 | 키·제약 | 이유 |
|---|---|---|
| guild | PK(guild_id) | 이름이 바뀌어도 같은 길드로 식별 |
| settlement_job | PK(job_id), UNIQUE(season_id, settlement_date) | 같은 시즌·날짜의 정산 중복 생성 방지 |
| score_event | PK(event_id) | 길드별 점수 이벤트를 각각 구분 |
| settlement_result | PK(job_id, guild_id) | 같은 정산·길드의 결과 중복 저장 방지 |
| guild_wallet | PK(guild_id) | 길드당 지갑 최대 하나만 생성 |
| settlement_chunk | PK(job_id, chunk_no) | 정산별 청크 구분, 완료 여부 기록 |

결과 테이블의 `(job_id, guild_id)`를 PK로 지정했습니다. 같은 길드는 다른 job에서 다시 보상을 받을 수 있지만, 같은 job의 결과는 두 번 저장할 수 없습니다.

이 PK만으로 보상이 지갑에 두 번 더해지는 것까지 막지는 못합니다. 결과 저장, 잔액 증가, 청크 완료 기록을 하나의 트랜잭션에서 처리해야 합니다. 정산 프로그램은 아직 구현 전입니다.

## FK를 두지 않은 이유

| 담당 | 확인할 내용 |
|---|---|
| 생성기 | 정산·길드 존재 확인, 청크 범위 설정 |
| 검증기 | 없는 정산·길드를 참조하는 행, 처리 대상 누락 확인 |
| 관리자 | 실험 중 정산·길드 삭제 및 확정된 입력 변경 금지 |

데이터를 입력하는 경로가 제한된 실험이므로 FK는 사용하지 않습니다. Python 생성기에서 정산·길드의 존재 여부를 확인하고, 검증기에서 잘못된 ID와 누락된 대상을 다시 확인할 예정입니다. 두 프로그램은 아직 구현 전입니다. 현재 DB는 해당 정산이나 길드가 없어도 양수 ID를 가진 행을 저장할 수 있습니다.

청크의 시작·끝 ID는 처리할 범위를 지정하는 값입니다. 해당 ID의 길드가 실제로 존재할 필요는 없습니다. DB에서는 두 ID가 양수인지, 시작 ID가 끝 ID 이하인지만 검사합니다. 실험 데이터는 관리자 계정으로 초기화합니다.

## 자료형과 CHECK

| 선택·제약 | 이유 |
|---|---|
| ID·점수·보상·잔액 BIGINT | 큰 정수 저장, 점수·보상의 부동소수점 오차 방지 |
| ID 직접 입력 | 같은 seed로 생성한 데이터와 기대값 파일의 ID 일치 |
| 업무 날짜 DATE, 시각 TIMESTAMPTZ | 정산 날짜와 기록 시각 구분, 세션 시간대 UTC 설정 |
| 필수 컬럼 NOT NULL | 값 누락 차단 |
| ID·청크 번호 > 0 | 1부터 시작하는 생성 규칙 적용 |
| 이름의 btrim 길이 1~100 | 빈 이름·일반 공백만 있는 이름·100자 초과 이름 거부 |
| 점수·보상·잔액 >= 0 | 0 이상인 값만 허용 |
| reward_points = total_score / 100 | 보상 공식 검사 |
| first_guild_id <= last_guild_id | 시작 ID가 끝 ID보다 큰 청크 거부 |
| balance 기본값 0 | 지갑 초기 잔액 0 |

점수가 0 이상이므로 정수 나눗셈 결과는 설계서의 FLOOR와 같습니다. 점수 199의 보상은 1입니다. 합계와 누적 잔액이 BIGINT의 저장 범위를 넘지 않는지도 생성기에서 확인해야 합니다.

CHECK는 NULL을 막지 못하므로 필수 값에는 NOT NULL을 함께 사용했습니다. 보상 CHECK는 저장된 합계와 보상의 관계만 검사합니다. 합계가 맞는지는 데이터 생성 때 별도로 계산한 기대값과 비교해야 합니다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/18/ddl-constraints.html)

## 정산 상태

| 규칙 | 이유 |
|---|---|
| TEXT + CHECK로 DRAFT·READY·COMPLETED만 허용 | 입력 준비·입력 확정·정산 완료 구분, ENUM 대신 TEXT 사용 |
| 기본값 DRAFT | 입력 적재 전 job 생성 |
| READY·COMPLETED에서 input_cutoff 필수 | 입력 확정 시각 기록 |
| COMPLETED에서만 completed_at 존재 | 완료 상태와 완료 시각을 함께 기록 |
| completed_at >= input_cutoff | 입력 확정보다 이른 완료 시각 거부 |

현재 CHECK는 한 행의 상태와 시각을 검사합니다. 완료 상태를 이전 상태로 되돌리거나, 처리하지 않은 청크가 있는데 정산을 완료로 표시하는 것까지 막지는 못합니다. 상태 변경 순서와 전체 청크의 완료 여부는 정산 프로그램에서 확인해야 합니다.

## 계정별 권한

lab_admin은 모든 DB 권한을 가진 로컬 관리자 계정입니다. 테이블 생성, 데이터 적재, 초기화, 장애 실험에 사용합니다. lab_worker에는 정산에 필요한 권한만 부여했습니다.

| lab_worker 권한 | 용도 |
|---|---|
| 6개 테이블 SELECT | 입력 집계·완료 여부 조회·잔액 확인 |
| settlement_result INSERT | 길드별 결과 기록 |
| guild_wallet UPDATE(balance) | 보상을 잔액에 더하기 |
| settlement_job UPDATE(state, completed_at) | 정산 완료 표시 |
| settlement_chunk UPDATE(completed_at) | 청크 완료 표시 |

입력 수정, 결과 덮어쓰기·삭제, 청크 범위·입력 확정 시각 변경, 테이블 생성 권한은 부여하지 않았습니다. 지갑 생성 권한도 없으므로 정산 전에 관리자 계정으로 지갑을 만들어야 합니다.

청크 잠금에 사용하는 SELECT FOR UPDATE에는 UPDATE 권한도 필요합니다. completed_at에만 UPDATE 권한을 부여해도 청크 잠금이 가능한 것을 확인했습니다. [PostgreSQL 권한 문서](https://www.postgresql.org/docs/18/sql-grant.html)

작업자가 수정할 수 있는 컬럼만 지정한 구성입니다. 작업자가 잔액을 임의로 바꾸거나 처리가 끝나기 전에 완료로 표시하는 것까지 막지는 못합니다. 작업자는 입력을 수정할 권한이 없지만 관리자는 수정할 수 있습니다. 따라서 관리자도 확정된 입력을 변경하지 않아야 합니다.

## 인덱스와 적용 방식

score_event에는 PK 인덱스만 두었습니다. 이 상태를 기준으로 `(job_id, guild_id)` 인덱스와 score를 포함한 커버링 인덱스의 효과를 비교합니다.

스키마 생성과 권한 부여는 하나의 트랜잭션으로 묶었습니다. 중간에 실패하면 일부 테이블만 남지 않도록 한 것입니다. CREATE TABLE IF NOT EXISTS는 기존 테이블이 있으면 구조를 확인하지 않고 넘어가므로 사용하지 않았습니다.

## 검증 결과와 남은 작업

실제 DB에서 다음 항목을 확인했으며, 검증 데이터는 롤백했습니다.

| 항목 | 결과 |
|---|---|
| 길드 ID 중복, 같은 시즌·날짜의 정산 중복, 같은 정산·길드의 결과 중복 | 저장 거부 |
| 6개 테이블의 FK | 0개 |
| 존재하지 않는 정산·길드의 양수 ID, 실제 길드가 없는 청크 경계 ID | 저장 허용 |
| 정산·길드 ID 또는 청크 경계 ID가 0인 행 | 저장 거부 |
| 음수 점수·잔액, 잘못된 보상, 시작·끝이 뒤집힌 청크 | 저장 거부 |
| 완료 시각 없는 COMPLETED 상태 | 변경 거부 |
| 작업자의 조회·청크 잠금·결과 저장·허용된 컬럼 수정 | 성공 |
| 작업자의 입력 수정·결과 덮어쓰기/삭제·청크 범위 변경·테이블 생성 | 권한 오류 |
| score_event 인덱스 | PK 인덱스 1개 |

현재 DB 제약은 청크 범위가 겹치는지, 처리 대상 길드가 빠졌는지까지 검사하지 않습니다. 생성기에서 정산별 대상 길드와 청크 범위를 확정하고 정산 중에는 바꾸지 않아야 합니다. 이벤트가 없는 길드의 0점 결과도 정산기가 생성해야 합니다.

다음 단계에서는 청크별로 정산을 처리하는 프로그램과 기대값을 비교하는 검증기를 구현합니다. 여러 작업자를 동시에 실행하거나 장애 후 다시 실행했을 때도 결과와 잔액이 맞는지 검증합니다.
