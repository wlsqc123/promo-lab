# 정산 스키마 설계 근거

작성일: 2026-10-13  
구현: `sql/schema.sql`, `sql/init.sql` · 검증: `sql/check_schema.sql`

## 테이블과 키

입력, 정산 결과, 누적 잔액, 처리 이력을 따로 저장합니다. 장애가 생겼을 때 원본과 결과를 비교하고, 완료한 청크를 확인하기 위한 구성입니다.

| 테이블 | 키·제약 | 이유 |
|---|---|---|
| guild | PK(guild_id) | 이름 변경과 무관한 길드 식별 |
| settlement_job | PK(job_id), UNIQUE(season_id, settlement_date) | 동일 시즌·날짜의 정산 중복 생성 차단 |
| score_event | PK(event_id) | 길드당 여러 점수 이벤트 저장, 개별 이벤트 식별 |
| settlement_result | PK(job_id, guild_id) | 동일 정산·길드의 결과 중복 저장 차단 |
| guild_wallet | PK(guild_id) | 길드당 지갑 최대 하나만 생성 |
| settlement_chunk | PK(job_id, chunk_no) | job별 청크 식별, 완료 여부 기록 |

결과의 `(job_id, guild_id)`가 중복 방지 기준입니다. 같은 길드는 다른 job에서 다시 보상을 받을 수 있지만, 같은 job의 결과는 두 번 저장할 수 없습니다.

이 PK만으로 지갑의 중복 갱신까지 막지는 못합니다. 결과 INSERT·지갑 UPDATE·청크 완료 갱신을 같은 트랜잭션으로 묶어야 합니다. 정산 프로그램은 아직 구현 전입니다.

## 참조 데이터 관리

| 담당 | 확인할 내용 |
|---|---|
| 생성기 | job·guild 존재 확인, 청크 범위 구성 |
| 검증기 | 고아 데이터·대상 누락 확인 |
| 관리자 절차 | 실험 중 확정된 job·guild 삭제 및 입력 변경 금지 |

FK는 사용하지 않습니다. 쓰기 경로가 제한된 실험이므로 참조 확인은 Python 생성기와 검증기에 맡깁니다. 두 프로그램은 아직 구현 전이며, 현재 DB는 존재하지 않는 양수 job·guild ID도 허용합니다.

청크 양 끝은 실제 길드의 존재와 무관한 범위 경계값입니다. 양수 여부와 시작·끝 순서만 DB에서 검사합니다. 실험 데이터 초기화는 관리자 계정으로 수행합니다.

## 자료형과 CHECK

| 선택·제약 | 이유 |
|---|---|
| ID·점수·보상·잔액 BIGINT | 큰 정수 저장, 점수·보상의 부동소수점 오차 방지 |
| ID 직접 입력 | 고정 seed와 기대값 파일의 동일 ID 재현 |
| 업무 날짜 DATE, 시각 TIMESTAMPTZ | 정산 대상 날짜와 실제 시점 구분, 세션 UTC 사용 |
| 필수 컬럼 NOT NULL | 값 누락 차단 |
| ID·청크 번호 > 0 | 1부터 시작하는 생성 규칙 적용 |
| 이름의 btrim 길이 1~100 | 빈 이름·일반 공백만 있는 이름·100자 초과 이름 거부 |
| 점수·보상·잔액 >= 0 | 설계서의 비음수 조건 적용 |
| reward_points = total_score / 100 | 보상 공식 검사 |
| first_guild_id <= last_guild_id | 역방향 청크 범위 거부 |
| balance 기본값 0 | 설계서의 지갑 시작값 반영 |

비음수 정수의 나눗셈은 설계서의 FLOOR와 같습니다. 점수 199의 보상은 1입니다. BIGINT에도 상한이 있으므로 생성기에서 합계와 누적 잔액의 범위를 확인해야 합니다.

CHECK는 NULL을 막지 못하므로 필수 값에는 NOT NULL을 함께 사용했습니다. 보상 CHECK는 저장된 합계와 보상의 관계만 검사합니다. 합계가 원본 이벤트와 일치하는지는 독립 기대값으로 검증해야 합니다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/18/ddl-constraints.html)

## job 상태

| 규칙 | 이유 |
|---|---|
| TEXT + CHECK로 DRAFT·READY·COMPLETED만 허용 | 적재 중·입력 확정·정산 완료 구분, 별도 ENUM 미사용 |
| 기본값 DRAFT | 입력 적재 전 job 생성 |
| READY·COMPLETED에서 input_cutoff 필수 | 입력 확정 시각 기록 |
| COMPLETED에서만 completed_at 존재 | 상태와 완료 시각의 불일치 차단 |
| completed_at >= input_cutoff | 입력 확정보다 이른 완료 시각 거부 |

현재 CHECK는 한 행의 상태와 시각을 검사합니다. 상태를 거꾸로 되돌리는 변경이나, 미완료 청크가 있는데 job을 완료로 표시하는 변경까지 막지는 않습니다. 상태 전이와 전체 완료 판정은 정산 프로그램에서 처리해야 합니다.

## 계정별 권한

lab_admin은 테이블 생성, 데이터 적재, 초기화, 장애 실험을 담당하는 로컬 슈퍼유저입니다. lab_worker에는 정산에 필요한 권한만 부여했습니다.

| lab_worker 권한 | 용도 |
|---|---|
| 6개 테이블 SELECT | 입력 집계·완료 여부 조회·잔액 확인 |
| settlement_result INSERT | 길드별 결과 기록 |
| guild_wallet UPDATE(balance) | 잔액 누적 |
| settlement_job UPDATE(state, completed_at) | 정산 완료 표시 |
| settlement_chunk UPDATE(completed_at) | 청크 완료 표시 |

입력 수정, 결과 덮어쓰기·삭제, 청크 범위·cutoff 변경, 업무 테이블 생성은 차단했습니다. 지갑 생성 권한도 없으므로 관리자가 정산 전에 지갑을 준비해야 합니다.

청크 잠금에 사용하는 SELECT FOR UPDATE에는 UPDATE 권한도 필요합니다. completed_at의 컬럼 권한으로 잠금 쿼리가 성공하는 것을 확인했습니다. [PostgreSQL 권한 문서](https://www.postgresql.org/docs/18/sql-grant.html)

이 권한 구성은 변경 가능한 컬럼을 제한합니다. 임의의 잔액 설정이나 이른 완료 표시까지 막는 구조는 아닙니다. READY 이후 입력 불변도 작업자에게만 강제되므로, 관리자는 확정된 입력을 수정하지 않아야 합니다.

## 인덱스와 적용 방식

score_event에는 PK 인덱스만 두었습니다. 이후 `(job_id, guild_id)`와 score를 포함한 커버링 인덱스의 효과를 비교하기 위한 대조군입니다.

스키마 생성과 권한 부여는 하나의 트랜잭션으로 묶었습니다. 중간에 실패하면 일부 테이블만 남지 않도록 한 것입니다. 기존 구조와의 차이를 숨기지 않도록 CREATE TABLE IF NOT EXISTS는 사용하지 않았습니다.

## 검증 결과와 남은 작업

실제 DB에서 다음 항목을 확인했으며, 검증 데이터는 롤백했습니다.

| 항목 | 결과 |
|---|---|
| 중복 길드·시즌/날짜·정산 결과 | 저장 거부 |
| 업무 테이블의 FK | 없음 확인 |
| 존재하지 않는 양수 job·guild ID, 길드가 없는 청크 경계 | 저장 허용 |
| 0인 참조 ID·청크 경계 | 저장 거부 |
| 음수 점수·잔액, 잘못된 보상, 역방향 청크 | 저장 거부 |
| 완료 시각 없는 COMPLETED 상태 | 변경 거부 |
| 작업자 조회·청크 잠금·결과 입력·허용 컬럼 갱신 | 성공 |
| 작업자 입력 수정·결과 덮어쓰기/삭제·범위 변경·DDL | 권한 오류 |
| score_event 인덱스 | PK 하나인 기준 상태 확인 |

청크 범위의 중복·누락과 job별 대상 길드 목록은 현재 제약으로 보장하지 않습니다. 생성기에서 목록을 확정하고 정산 중에는 고정해야 합니다. 이벤트가 없는 길드의 0점 결과도 정산기가 생성해야 합니다.

다음 단계는 청크 단위 트랜잭션과 독립 검증기 구현입니다. 동시 실행과 장애 후 재실행에서도 결과·지갑이 일치하는지는 그 단계에서 검증합니다.
